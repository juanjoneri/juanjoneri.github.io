# Private-project standard (v1)

Every private project registered on https://juanjoneri.github.io follows this standard. The goal: if a machine
dies, a new Claude (or Juan) clones the repo, runs `./setup`, and the project continues exactly where it was. The
shared tooling is `kit/sitekit.py` in this repo (Python 3.9+, standard library only, plus `git` and `age`).

A project is compliant when it passes the **acceptance test** (§8). Rules are numbered so reviews can cite them.

---

## 1. One repo per project, one parent directory

1.1 The registered repo `juanjoneri/<slug>` holds all code, configuration and docs needed to run the project.
No project logic lives only on a machine, and nothing is copied in from another folder.

1.2 On every machine, every project lives at **`~/Code/<slug>`**: one shared parent, the folder named after the
repo. Not on the Desktop (macOS privacy prompts) or in iCloud. `SITE_PARENT` overrides the parent for tests.

1.3 Hand-edited files stay in git as text: docs, configs, decisions (e.g. `landmarks.json`, overrides, rules).
Their diffs are useful and they are small.

## 2. Repo shape

```
<slug>/
  site.json        manifest (§3): jobs, schedules, state, secrets, tools, manual steps
  setup doctor run executable wrappers around .kit/sitekit.py (copy from kit/template/)
  .kit/sitekit.py  vendored copy of the hub's kit/sitekit.py; site.json "kit" records the hub commit it came from
  RECOVERY.md      generated by `sitekit.py recovery` from site.json; never edited by hand
  status.json      reporting (§7), written by `run`
  CLAUDE.md        project instructions, including its own redaction rules (§9.3)
  state/           gitignored: raw.db, state.db, caches
  .state-branch/   gitignored: local checkout of the `state` branch
```
Append `kit/template/gitignore` to `.gitignore`.

| Command | Does |
|---|---|
| `./setup` | runs `site.json` `setup` commands, restores state if missing, installs this machine's schedules, runs `./doctor` |
| `./setup --update <hub sha>` | replaces `.kit/sitekit.py` with the hub's copy at that commit and records it in `site.json` |
| `./doctor [--quick]` | ✅/❌ for location, kit, tools, secrets, state, jobs, schedules, portability, project checks, offline build |
| `./run <job> [--offline] [--no-push]` | runs one job (§6); `--offline` runs its `offline_command` from the restored state only |
| `python3 .kit/sitekit.py ingest <source> <paths…>` | adds source files to the raw store (§4) |
| `python3 .kit/sitekit.py save` / `restore` | encrypt + push / fetch + decrypt the state (§5) |
| `python3 .kit/sitekit.py keygen` | creates the repo's age key pair once (§5.4) |
| `python3 .kit/sitekit.py recovery` | rewrites RECOVERY.md |

Code updates are deliberate. Schedules run the code checked out at setup, and nothing pulls code automatically.
Data-only paths a project declares (e.g. purchase-receipts' `rules/`) may be pulled by the job itself.

## 3. `site.json`

See `kit/template/site.json` for a complete example.

| Key | Meaning |
|---|---|
| `slug`, `repo`, `kit` | repo name; `owner/name`; hub commit of `.kit/sitekit.py` |
| `setup` | shell commands `./setup` runs (venv, `uv sync --frozen`, `npm ci`, …) |
| `tools` | `{cmd, version?, match? (regex on the version line), fix, required?}` |
| `secrets` | `{name, where: keychain\|actions, jobs?, keychain? (legacy Keychain service to map), fix}` |
| `state` | `{raw_db?, state_db?, warm: [paths], exclude: [globs], keep: 7, recipient}` (§4, §5) |
| `jobs` | list of jobs (§6) |
| `build_offline` | command that builds the outputs from the restored state, offline (§8) |
| `checks` | extra doctor checks `{name, cmd, on? mac\|linux, slow?, fix, required?}` |
| `manual` | steps no script can do (sign-ins, OS permissions, app installs), listed in RECOVERY.md |
| `mac_paths_ok` | files allowed to contain macOS-only paths (update-only code; never the build path) |

## 4. State: what is kept, and where

4.1 **Three kinds of data.**
- **Irreplaceable machine-produced state** → `state.db` (SQLite). Examples: append-only logs, run history, decisions a
  job made. Optional: a project without such state has no `state.db`.
- **Source data** (exports, API snapshots, downloads) → the **raw store** `raw.db` (§4.2).
- **Everything rebuildable**, including parsed tables, → caches, gitignored, recreated by the jobs. A cache that is
  slow to rebuild (hours of throttled API calls) may be listed in `state.warm` and is saved weekly.

4.2 **Raw store: lossless.**
`raw_files(id, source, path, sha256 UNIQUE, bytes, mtime, imported_at, media_type, compression, meta JSON, segment,
content)`.
- Every source file is stored byte for byte, compressed (zlib) when that saves ≥10%. `.gz` and other compressed
  files are kept as they are.
- Paths keep the original relative path, so loaders that match on globs keep working.
- **Zips are unpacked** into one row per member, `path = "export.zip!/dir/file"`, with the member's date and CRC in
  `meta`. Nested zips are unpacked too, up to 3 levels deep.
- **Password-protected zips** are stored whole, with their member names in `meta`; the password goes in the password
  manager. Ingest the extract separately.
- **Duplicates** are stored once (by sha256). Every path a file was seen at is recorded in `sightings`.
- **Exclusions:** `state.exclude` globs on `"<source>/<path>"` (e.g. `oura/*payment*`) are recorded in `excluded` by
  name, size and hash only, never their content. Every exclusion must be approved by Juan and listed in CLAUDE.md.
- Project fields such as dataset or span go in `meta` (`ingest --meta '{…}'`) or in a project table keyed by `sha256`.

4.3 **Parsed tables** are built from `raw.db` into a cache, with a `raw_file_id` / sha256 + record key back to the
source and the unmodeled fields kept (an `extra` JSON column, or long-tail metric tables). A better parser just
rebuilds them.

4.4 **Plaintext outputs** (`site/index.html`, `tabs.json`, CSVs on `main`) are allowed in the private repo if they
show nothing more than the encrypted page does, and they follow the project's redaction rules (§9.3).

## 5. Saving and restoring state

5.1 `run` saves after every successful job; `save` can also be run by hand. Everything goes to an orphan
**`state` branch** of the same repo, force-pushed as a single commit, never to `main`:
```
manifest.json                 segments, state copies, warm caches, hashes
raw/<ts>-<n>.age[.000…]       raw segments: encrypted ONCE, never rewritten
raw/index.age                 exclusions + sightings (small, rewritten each save)
state/state-<ts>.age          consistent copy of state.db (VACUUM INTO), last 7 kept
warm/<path>.age               warm caches, at most weekly
```

5.2 **Raw segments are append-only and immutable.** A segment is an SQLite file with the rows not yet saved, at
most 256 MB. It is encrypted once and never rewritten, so its git object never changes: each save uploads only new
segments. Rows are marked saved only after the push that carries them succeeds.

5.3 **Size limits.**
- Encrypted files are split into 90 MB parts (GitHub's file limit is 100 MB).
- A save pushes in batches of at most 1 GB (GitHub rejects pushes over 2 GB).
- A repo should stay under 4 GB; `doctor` is the place to watch it. Past that, move raw segments to Release assets
  (a future kit version).

5.4 **Encryption: [age](https://age-encryption.org) with a key pair per repo.**
- `keygen` writes the **public** key to `site.json` `state.recipient` (commit it) and prints the private key once.
- Save the private key in the password manager as `<slug> / STATE_AGE_KEY`.
- Jobs encrypt with the public key, so a machine never needs the private key to save. It is needed only to restore.
- Raw data is never committed unencrypted.

5.5 **Restore.** `restore` (called by `setup` when state is missing):
- decrypts every segment and checks it against the manifest hash;
- rebuilds `raw.db` and checks every file's sha256;
- restores the newest `state.db` and the warm caches;
- needs `STATE_AGE_KEY` (§6.4); keeps any existing local files as `*.bak` with `--force`.

## 6. Jobs, schedules, secrets

6.1 A job is a unit of work with one place it runs:
```json
{"name": "pull", "runs_on": "mac" | "actions" | "linux",
 "command": "…",               "offline_command": "…",   "outputs": ["site/index.html"],
 "secrets": ["KUBERA_AUTH_TOKEN"],
 "schedule": [{"cron": "0 7,10 * * 1-5", "tz": "America/Los_Angeles"}],
 "freshness": {"mode": "alert", "grace_minutes": 90} | {"mode": "reminder", "every_days": 30},
 "launch": "direct" | "terminal"}
```
A project can have several jobs in different places (e.g. github-pages: `market` on Actions, `portfolio` on the Mac).

6.2 `./run <job>` on a machine does the following:
1. Takes a lock.
2. Exports the job's secrets as environment variables and runs `command`.
3. Saves the state.
4. Writes `status.json`.
5. Commits `outputs` + `status.json` as **one commit on top of `origin/main`**. It never takes code from GitHub, and it
   retries on conflicts. That push triggers the publish.

On failure it records the failed step and exit code, pushes `status.json` alone, and posts a macOS notification.
Each project's `command` reads its secrets from the environment.

6.3 **Schedules.**
- `cron` + IANA `tz`. `sitekit` computes due times DST-correctly, and skips wall times that don't exist (the spring
  DST gap).
- On a Mac, `./setup` installs one LaunchAgent per job (`site.<slug>.<job>`) from the schedule. Write mac schedules
  in the Mac's own time zone; launchd fires in local time.
- `"launch": "terminal"` runs the job inside Terminal, for jobs that need Terminal's Full Disk Access.
- Actions jobs keep their cron in the workflow (UTC) and repeat it in `site.json` for reporting.

6.4 **Secrets have one name everywhere.**

| Where | Name |
|---|---|
| password manager | `<slug> / <NAME>` (the master copy) |
| Mac Keychain | `site/<slug>/<NAME>` (`security add-generic-password -s site/<slug>/<NAME> -a "$USER" -w` prompts for the value) |
| GitHub Actions secret | `<NAME>` |
| Linux / tests | env `<NAME>` or `~/.config/site/<slug>/<NAME>` |

Never in config files, Claude configs, `.bak` files or logs. `doctor` checks presence without printing. Mac jobs push
with a **write deploy key limited to their own repo**, not an account-wide SSH key.

## 7. Reporting

7.1 Every job's health is shown **inside the project's own (encrypted) page**. The public landing page shows only a
warning sign when a project needs attention: no job names, no times, no errors.

7.2 `status.json` (in the repo, written by `run`, or by the publish workflow for Actions jobs via `job:` in `site.yml`)
records per job:
- `result` (ok/failed), `step`, `code`;
- `last_run`, `last_ok`;
- `stale_after`, which is schedule-aware: the next scheduled run after the last success, plus grace. So a weekend gap
  is not an alert. For `reminder` jobs it is `last_ok + every_days`.

7.3 **Every page includes the status block:**
```html
<div data-site-status="<slug>"></div>
<script src="/assets/status.js"></script>
```
The publish workflow embeds the full `status.json` into these pages **before encryption** (`status_publish.py`).
`status.js` renders one line per job (✅ ok · ⚠️ stale · ❌ failed at <step> · ⏳ reminder), evaluated against the
viewer's clock. A job that silently stopped turns stale without any redeploy.

7.4 Publicly, each site publishes only `{"version": 2, "slug", "failed", "ok_until"}`. The landing page shows ⚠️ right
after the site's name when `failed` is true or `ok_until` has passed, and nothing otherwise. `status_check.py` validates both formats.
Anything else is dropped.

## 8. Acceptance test

A project is compliant when all of these pass:
1. On a **clean machine or cloud container**: `git clone` into `~/Code/<slug>` → `./setup` (with `STATE_AGE_KEY`) →
   `./doctor` shows ✅ ready. Warnings are allowed only for runtime-only pieces (Mac apps, sign-ins), and each must
   say exactly what is missing and how to fix it.
2. `./run <job> --offline` (or `build_offline`) produces **the same outputs as the current setup from the same raw
   snapshot and frozen cache**. Every project needs an offline mode; live data can't be compared.
3. `build` runs on Linux: no hard-coded macOS paths in the build path (e.g. a font with a fallback). `doctor` scans
   for them.
4. On the real runtime: `./run <job>` succeeds, `status.json` shows ok, the `state` branch moves, and the page's status
   line is ✅.

## 9. Migration and documentation

9.1 Migrations write to both the old and the new storage until they are proven equivalent:
- row counts and sha256 match;
- the exported logs are byte-identical;
- the outputs are identical.

Old files are then moved to `_to_delete/` (never deleted) and removed after a month.

9.2 `RECOVERY.md` is generated (`sitekit.py recovery`). `site.json` is the source of truth for every
dependency, so docs can't drift.

9.3 Each project's `CLAUDE.md` lists:
- what the project shows;
- its data sources and their exclusions;
- its redaction rules (e.g. purchase-receipts never reveals Gift-tagged purchases);
- its jobs;
- anything a new Claude must not touch (e.g. append-only logs).

## 10. Adopting the standard in a project

```bash
cd ~/Code/<slug>
mkdir -p .kit && curl -fsSL https://raw.githubusercontent.com/juanjoneri/juanjoneri.github.io/<sha>/kit/sitekit.py -o .kit/sitekit.py
cp <hub>/kit/template/{setup,doctor,run} . && cat <hub>/kit/template/gitignore >> .gitignore
# write site.json (start from kit/template/site.json), then:
python3 .kit/sitekit.py keygen            # save the printed private key in the password manager
python3 .kit/sitekit.py recovery
./doctor
```
Then:
1. Ingest the sources and run the jobs.
2. Add the status block (§7.3) to the page, and `job:` to `site.yml` for Actions jobs.
3. Bump `site.yml`'s pinned hub commit to one that includes this kit.
4. Run the acceptance test.
